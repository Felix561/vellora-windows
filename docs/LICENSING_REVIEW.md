## Decision in plain language

Open-sourcing a Windows `.exe` application is an ordinary, supported distribution model. The executable format does not make a program proprietary or require a Microsoft license for your own code. Vellora can expose its source and build instructions under MIT and separately offer an installer, provided it has rights to the material it distributes and fulfills dependency conditions. MIT permits redistribution, modification, and sale while requiring retention of its copyright and permission notice. [OSI MIT license](https://opensource.org/license/mit).

The current source has a consistent MIT declaration in `LICENSE`, `package.json`, and `src-tauri/Cargo.toml`. Felix Seitzer's existing copyright credit remains as requested. It is not a claim to ownership of third-party libraries, Windows, OpenAI models, or every potentially unprotectable AI-generated element. Windows-only scope is compatible with an open-source release.

Source publication and installer publication are separate decisions. The current replacement artwork now has [documented generation provenance](ARTWORK_PROVENANCE.md). Source publication still needs final privacy/security review and approval of its clean-history boundary; old artwork remains unverified in private history. Public installer distribution also needs its exact-version notices, source-availability obligations, native testing, checksums, and a signing/trust decision. Signing establishes publisher/integrity information; it does not supply copyright permission or establish license compliance. This candidate uses an NSIS executable installer, not MSIX; Microsoft's [Authenticode overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/authenticode) explains the separate trust mechanism.

## Native notice gap closed in source; binary remains a review artifact

The original notice generator covered Cargo/npm packages, but not the separate NSIS tool distribution, additional plugin DLL, or Microsoft loader bytes. [Supplemental native notices](../THIRD_PARTY_NOTICES_NATIVE.md) now include the inspected versions, license texts, source links, hashes, and scope distinctions. The application packaging must include this supplemental file alongside `LICENSE` and the main notices. An older installer cannot acquire new resources through a documentation change.

The private preparation now includes [source-companion generation](../.github/scripts/prepare-release-sources.mjs) and [installer verification](../.github/scripts/verify-review-installer.ps1). The source companion preserves the five reviewed MPL crate archives byte-for-byte, checks their SHA256 against `Cargo.lock`, and includes the exact NSIS 3.11 source archive. The official NSIS archive for commit `7359413009afd4f0fff472d841fc2f2cc0e0a5f8` has SHA256 `48c2b3b70e44b3df355e580e83c4107ff1e5b9ba4d7966bc9950aff0ab7d72ac`; its `COPYING` and LZMA/installer sources were verified during preparation. This is a prepared private companion, not a public source-download service. A private Actions artifact with limited retention does not fulfill an ongoing public binary release's source availability.

For the eventual public installer:

1. Ensure its build uses the versions described in these notices; refresh native provenance on tool/plugin/SDK changes.
2. Make notices available with the installer download and install the three notice/license resources. A bare executable separated from its required notices is not a complete redistribution package.
3. Publish the prepared exact-source companion to a durable public release location and tell installer recipients where to obtain it; retain a retrievable copy of the exact covered MPL and NSIS LZMA source. Preserve original license headers. No covered dependency source patches were found in this repository; if any are introduced, distribute those changes under the applicable license.
4. Compare installed resource hashes to committed notices on the exact release candidate. Publish an installer checksum and clearly disclose signing status and known limitations.

## AI-created code and branding provenance

The owner reports building Vellora solely with AI agents and retaining Felix Seitzer credits. No external human/employer source contribution was stated. This supports the recorded project history but is not an independent title search, AI-output uniqueness guarantee, or verification that generated code never reproduced another work.

OpenAI's current European terms assign its rights, if any, in output to the user to the extent permitted by law; they also say output can be nonunique, third-party output is excluded, and users must respect others' rights. API/business use has separate terms; record which service/account terms applied if original generation records are recovered. [OpenAI Europe terms, Content](https://openai.com/policies/eu-terms-of-use/).

German copyright protects personal intellectual creations; the DPMA explains that wholly AI-generated output is not protected, while AI as a tool needs a case-specific assessment. Therefore a copyright credit/MIT file does not manufacture exclusive copyright in material that lacks protectable human creation, nor erase upstream rights. It remains useful to license any rights actually held in the project's creative selection, modifications, documentation, and other protectable contributions, while keeping dependency licenses. [UrhG section 2](https://www.gesetze-im-internet.de/urhg/__2.html?lang=de), [DPMA on AI output and software](https://www.dpma.de/service/schutzrechte_kurz_erklaert/geistigeseigentumdigital/index.html).

## Publication history options

Replacing an asset in the current source tree does not remove its earlier bytes from Git history. The owner's authorization to replace the logo throughout the current application does not itself authorize rewriting remote history or a force push.

The recommended publication route is a reviewed clean source snapshot in an independent repository history, keeping the current audit/development repository private. Preparing a local export or a separate local clean-history candidate is reversible; creating a remote repository or changing visibility still waits for the final approval. This avoids distributing earlier unverified asset blobs and development history while preserving the private record.

To preserve the eventual `Felix561/vellora` repository name, a future approved sequence could rename the current repository to a private archive name, create a fresh repository at `Felix561/vellora`, and populate it from the reviewed independent snapshot. This is a proposed name-preserving option only: neither a rename nor a new remote nor public visibility is authorized or performed by the preparation. Before that sequence, review GitHub redirects, existing integrations, permissions, and the approved snapshot. The archive remains private; publication does not require destroying the development record.

An orphan publication branch inside the existing repository alone is insufficient isolation if that entire repository later becomes public: other branches, tags, pull-request history, or retained objects can still expose old content. Publishing the complete existing history instead requires an explicit historical-content decision after privacy and asset-rights findings are resolved. Describing uncertain historical assets as archival does not establish permission to redistribute them. A history rewrite is a separate disruptive operation requiring authorization and does not promise removal of copies elsewhere.

The clean snapshot must replace/remove old branding in every tracked current asset, including screenshots; an old screenshot containing the previous logo still distributes that logo even if application icons have changed. Preserve required third-party notices and source companions in the publication candidate.
